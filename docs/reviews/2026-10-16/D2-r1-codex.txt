VERDICT: REVISE

1. **BLOCKER — rollback leaves re-learned local windows in place.** `lane-D-time-meds-gamification.md:182,227` says downgrade drops only `adaptive_window_tz` and cleared windows stay NULL. But re-learn writes non-NULL windows (`src/backend/modules/adherence_patterns.py:491-504`), which the scheduler prefers over the tolerance fallback (`src/backend/modules/notification_scheduler.py:427-434`). After a revert, the old UTC scheduler can read local-time windows as UTC. Test `_005` downgrades before re-learn, so it misses this case (`lane-D-time-meds-gamification.md:200`). **Fix:** clear both window columns in downgrade before dropping the marker; test learn → downgrade → assert both windows are NULL.

2. **MAJOR — the hourly notification limit can delay re-learn beyond 60 seconds.** The plan claims re-learn runs on the first pass after unlock (`lane-D-time-meds-gamification.md:189,192`), but `_check_all_schedules` returns at the rate limit before iterating profiles (`src/backend/modules/notification_scheduler.py:279-293`). At the configured limit, re-learn can wait until the next hourly reset. **Fix:** run the re-learn check independently of the notification cap; add a test with the cap already reached.

3. **MAJOR — the learner can re-learn already-marked schedules when one schedule is unmarked.** The proposed method groups unmarked schedules by medication and calls `update_adaptive_windows` (`lane-D-time-meds-gamification.md:183`), while that method updates *all active schedules* for the medication (`src/backend/modules/adherence_patterns.py:470-478`). A new unmarked schedule can therefore rewrite existing schedules under a changed timezone, contrary to the one-time behavior in `lane-D-time-meds-gamification.md:190`. **Fix:** limit learning and marker writes to the collected unmarked schedule IDs; test a medication with marked and unmarked schedules in different timezones.

4. **MAJOR — concurrency safety is only established within one scheduler instance.** The per-profile lock is in memory (`src/backend/modules/notification_scheduler.py:141-143,284-293`); the proposed attempted set is also in memory (`lane-D-time-meds-gamification.md:185`). The marker’s conditional update comes after window writes (`lane-D-time-meds-gamification.md:183`), so it does not prevent two processes from starting the work. `main.py:81-83` starts a scheduler per app process; it does not prove only one process can serve a vault. Test `_010` uses one scheduler instance and cannot prove cross-process safety (`lane-D-time-meds-gamification.md:205`). **Fix:** document and enforce one process per vault, or add a durable claim before learning and test two scheduler instances against one vault.

5. **MINOR — the startup estimate bounds query count, not work or elapsed time.** The plan says each query handles “≤ 30 days of rows” (`lane-D-time-meds-gamification.md:192`), but `learn_time_window` loads every matching dose in that period with `.all()` (`src/backend/modules/adherence_patterns.py:201-216`). The scheduler holds the profile lock for the pass (`src/backend/modules/notification_scheduler.py:284-293`), so row volume can extend reminder delay. **Fix:** specify and validate a supported per-schedule row ceiling or a measured upper bound for the locked pass.
