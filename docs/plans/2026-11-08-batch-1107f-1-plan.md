## RULES-RANGE-VALUE

**Source:** triage-1107.md :127 (live candidates; safety kind; size M): "rules verifier marks a wrong value \"verified\" when the source range clause is echoed back | `be/modules/verifier_agent.py`, `be/tests` | safety | M | ask-first file; L0 tells owner". Lens: medical safety. **Owner gate: ANSWERED 2026-11-09 (RULES-VERIFIER-ASKFIRST, "narrow to measured values").** `verifier_agent.py` is on the CLAUDE.md always-ask list; the answer licenses this narrowing and nothing wider. (This section said "unanswered" until BATCH-1110A; a scan that read that word without the later ruling wrongly flagged the row as gated, see `recurring-failures.md`.)

**Facts (re-read on the base).**
- `verifier_agent.py:238-297` `_check_entailment_rules`: `claim_values = self._extract_values(claim)` then `value_matches = sum(1 for v in claim_values if v in source_values)` (`:273-277` region) — **any single** matched number is `ENTAILMENT` at `confidence = min(0.9, 0.6 + matches*0.1)` → 0.7 for one hit.
- A claim like "Your potassium of 9.0 is above the reference range 3.5-5.0" carries claim values `{9.0, 3.5, 5.0}`; a source that only echoes the range clause ("reference range 3.5-5.0") matches `3.5`/`5.0` → ENTAILMENT even when the source's measured value differs from 9.0 or is absent. The range bounds themselves satisfy the match — the actual value never has to agree.
- `_determine_verification` (`:430`) then verifies on `supporting` + faithfulness; the NLI path may only veto (`git log` `46d1d083` GC5-NLI-NEUTRAL: "NLI may only veto, rules decide") — so the rules false-positive is the deciding vote, not a hint.
- `_extract_values` (`:359`) is a plain number regex — it does not distinguish "measured value" from "range bound"; that distinction is the whole defect.
- Merged-check: `git log origin/main --oneline -- src/backend/modules/verifier_agent.py` → `46d1d083` NLI-veto, `9c08c9b6` predict-failclosed, `056749ff` NLI body, `dffe1f99` dead-config cleanup — none fixes the rules-side value match.

**Build.**
1. In `_check_entailment_rules`, split claim values into *measurement* values and *range-bound* values: any number that appears inside a range clause in the claim is a bound, not a measurement. **BATCH-1110A correction to the regex:** the first version of this plan wrote the connector as `[:is]?`. In a regex that is a character class, not a word: it matches one of `:`, `i` or `s`, so "range is 3.5-5.0" is not stripped (the connector "is" is two characters) and "range: 3.5-5.0" only works by accident. The connector is `(?:\s*:|\s+is)?`. The built pattern is `(?:(?:normal|reference)\s+)?range(?:\s*:|\s+is)?\s*\d+(?:\.\d+)?\s*[-\u2013\u2014]\s*\d+(?:\.\d+)?`, case-insensitive (build commit `e4268da2`; RED on `main` 9 failed / 6 passed, GREEN 15). A range written "3.5 mmol/L - 5.0", "70 to 99" or "ref: 3.5-5.0" is not stripped, by design: the clause is deliberately narrow. Require at least one **measurement** value to match the source for the ENTAILMENT branch; a bound-only match falls through to lexical overlap.
2. Mirror the same exclusion when extracting source values — a source's own "range X–Y" numbers must not supply the match for the claim's measured value either (claim 9.0 vs source "range 3.5-5.0" must stay NEUTRAL, not ENTAIL via 5.0).
3. Keep the contradiction patterns untouched. Deterministic rules only; no NLI changes (GC5-NLI-NEUTRAL's veto-only contract stays).

**Deviation accepted by the owner (RULES-RANGE-STRICT-CAP, "Keep the stricter cap (Recommended)", 2026-11-10).** The build widened the lexical-overlap cap: when either the claim or the source contains a range clause (or the bound-only match happened), the overlap score is capped at the score computed with range clauses stripped. Without it, a unitless "range is 3.5–5.0" shared tokens and scored 0.62, which was ENTAILMENT through the overlap branch. The cap makes more claims unverified, which is the fail-closed direction; it is owner-visible at merge.

**Tests (RED first).**

- **HC-RRV-003:** `verify_claim` end-to-end on the RRV-001 pair → `is_verified=False`, source lands in `neutral`, not `supporting`.
- **HC-RRV-004:** regression — a claim whose only value is the measured value and whose source repeats it → ENTAILMENT (rules path unchanged for the true-positive case).
- **Would not notice:** NLI model behaviour (rules-path test only); whether the pipeline upstream ever produces such a claim (planner note, not asserted).

**Files:** `be/modules/verifier_agent.py` (`_check_entailment_rules`/`_extract_values` region only), `be/tests/test_hc_a1_agent_verification.py` (append HC-RRV-001…004 to the existing verifier file — it is the rules/NLI home) or new `test_rules_range_value.py` if the class layout argues for it; pick at build and say which. **Not** `rag.py`, `faithfulness.py`, `interpret_safety.py`.
