## RECOVER-ORDER

**Source:** queue.md :550 (MVP pass bug table; ask-first `api/profiles.py:726-753`): "a master commit failing after key re-seal and recovery-file rotation leaves neither password nor code working." The fix preserves the invariant the code's own docstring already states — it closes the window the docstring missed. (BATCH-1110A: the earlier text of this plan said there was no owner gate and that `issue_recovery_code` was out of scope. Both statements contradicted the answer and were replaced.)

**Facts (re-read on `9ab89972`; `api/profiles.py` identical on `d563829d`).**
- `recover_profile` (`api/profiles.py:746-863`): malformed-code rejection `:797-801` (no PBKDF2 spent); DEK unsealed from the recovery seal `:803-811` (`_fail` commits the audit row itself at `:794`); primary key re-sealed under `payload.new_password` and written atomically `:825-826` (`_atomic_write` `:633-641` = tmp + `os.replace`); `profile.password_hash`/`password_salt`/`is_locked`/`last_accessed_at` set in memory `:828-831`; **the recovery code rotated at `:838`** — `_issue_recovery_code` (`:644-665`) writes *new* `key.recovery`/`key.recovery.method` files over the old ones, immediately; two audit events `:842-851`; the single `await db.commit()` at `:852`.
- **The dead window:** between `:838` (rotation done on disk) and `:852` (master commit), a process crash or a failed commit leaves: primary seal = new password, `password_hash` = old, recovery seal = the new code the client never saw. Old password can't unseal the new primary (and fails the old hash anyway); the old recovery code's file is gone → **neither credential works; the vault is unrecoverable.**
- The docstring `:760-764` claims the opposite ordering guarantee ("primary key files are replaced before the password hash is committed … login fails cleanly and the recovery code still works") — that guarantee holds only for crashes in `(:825, :838)`. After `:838` it stops being true. The comment stays load-bearing: the fix makes the invariant true for every window.
- `issue_recovery_code` (`:688-743`) rotates files at `:726` then commits audit `:741` — the same shape as `recover_profile` but a milder failure: the primary seal is untouched, so a failed commit leaves the working password and a rotated code the patient never saw (the stored code silently dies, and the patient can re-mint). The route returns the code only after commit (`:743`). **In scope by the owner answer** (the plan first called it out of scope): the same commit-before-rotation reorder applies.
- `issue_recovery_code`'s ordering is also why the fix shape is right: nothing downstream reads `new_code` until after the commit that should order it.
- `recovery_rate_limiter.reset(rate_key)` `:840` is in-memory — placement is free either side of the commits.
- `open_profile_database_on_login` `:854` + `_audit_fk_orphan_cleanup` `:855` run after commit and verify the new password opens the vault — the right last step under both orderings.

**Build.**
1. `api/profiles.py:838-852`: move the rotation after the first commit. Order becomes: `_atomic_write` primary pair (`:825-826` unchanged) → profile fields (`:828-831` unchanged) → `log_profile_event("recovered")` → **`await db.commit()`** → `new_code = _issue_recovery_code(profile_id, dek)` → `log_profile_event("recovery_code_generated")` → **`await db.commit()`** → `recovery_rate_limiter.reset(rate_key)` → `open_profile_database_on_login` + `_audit_fk_orphan_cleanup` (unchanged) → response.
